# Review and revised execution order — 22 October 2026

Verdict: keep the goal of real module boundaries, but revise the migration and
validation strategy before implementing it. The plan below is directionally
sound; it is not yet evidence that case1312 can be assembled cheaply. This review
supersedes its execution order and treats its numerical targets as provisional.
No compiler, accepted-unit rebuild, toolchain change or agent was started.

## Findings that change the plan

1. **The final consumer must participate in the module system.** In the installed
   Lean4.24 `Environment.lean`, `importModulesCore` explicitly loads all transitive
   private information when the root is a legacy file. Hiding a cut behind a new
   module then importing it from the old case root undoes the isolation. The new
   case root, eventual all-cases root, and audit entry points must be included in
   the design. Test this failure mode deliberately on fresh tiny fixtures.
   Likewise, a module root rejects direct legacy imports. The real semantic base
   and original contract dependencies are therefore a migration prerequisite,
   not a minor detail postponed until the twelve cuts are done.

2. **Audit composition is part of the architecture.** The current
   `audit/SharedAxiomAudit.lean` recursively examines kernel declaration bodies.
   Its Lean4.24 collector treats an exported axiom-shaped theorem as an axiom;
   simply keeping this traversal either fails acceptance or requires loading
   private implementations again. Restoring one giant private import at a
   checkpoint would recreate the resource failure. Use a stock module-aware
   axiom facility on a validated exact version, together with artifact-bound
   producer evidence. Test the bounded checkpoint path during the pilot.
   The unchanged legacy workflow remains authoritative until a separately
   validated replacement exists; this review does not alter its acceptance gate.

3. **A whole proof-body census is too expensive as the first milestone.** First
   map the small original-contract/type closure and direct case1312 interfaces
   from retained sources/manifests. Resolve hidden definitional dependencies as
   each boundary is built. A complete three-million-constant proof graph is not
   needed to establish whether module isolation works. Preserve the all-routes
   import census for assessing individual legacy-pruning proposals, but do not
   turn it into a second open-ended infrastructure project.

4. **A small cut API can still have a huge public dependency closure.** Four
   exported names are not a meaningful hard limit: their types, exposed values,
   instances, persistent extensions and executable dependencies matter. State
   cut results using the common semantic predicates and small explicit masks;
   prove representation equalities inside the producer. Separate genuinely
   computational public definitions from opaque proof implementation. Disable
   compatibility options that silently export private declarations/proofs in
   production modules, after verifying the chosen version's exact behavior.
   Measure serialized public bytes and loaded IR/extension state, not just names.

5. **One-time migration work cannot be wished away.** New modules cannot obtain
   checked proof bodies from old JSON receipts, and new Lean versions cannot use
   old oleans as proofs. Reusing old accepted sources may still require compiling
   a new representation of their proofs. Renaming that work a fresh replacement
   does not evade the no-accepted-unit-recompile instruction. Before migration,
   produce an explicit list of retained artifacts that can actually be reused,
   newly proved obligations, and accepted obligations requiring a port/rebuild.
   Escalate the latter scope for a user decision; do not silently initiate it.
   It is possible that the requested architecture requires this one-time cost.

6. **The original numerical targets are heuristics, not acceptance necessities.**
   Keep the actual3072MiB hard guard. Use measured baseline plus incremental
   interface cost to set soft budgets; do not reject a correct scalable design
   solely for exceeding100000constants or four exports. Conversely, a tenfold
   constant reduction does not establish fast imports or bounded memory. Require
   a growth experiment and an actual original-contract consumer. The eventual
   root will still grow with its public mathematical statements; the aim is to
   hide certificates and helper implementations, not promise constant space for
   an arbitrarily large theorem collection.

## Revised milestones and stop conditions

**A. Establish feasibility before broad census or migration.** Inspect the exact
module/audit APIs and the minimal original-contract foundation. Use fresh tiny
fixtures on an existing reservation to test producer -> intermediate module ->
consumer -> audit/checkpoint, including private data growth, accidental legacy
root behavior, exported computation, and forbidden-axiom propagation through
multiple interfaces. Check stock Lean rejects a false implementation. Missing or
mismatched producer evidence must fail project acceptance even when an interface
alone is sufficient for the compiler to elaborate a consumer. Keep these two
claims distinct. The existing4.24 collector is demonstrably unsuitable unchanged;
spend no open-ended effort patching its importer. If stock support requires an
upgrade, choose a pinned compatible Lean/Mathlib pair and document the disk/build
and accepted-proof migration scope before proceeding.

**B. Establish the real semantic foundation and one vertical slice.** Before
rebuilding a heavy cut, show that the actual original contract can be stated in
the intended small public foundation without legacy umbrella imports. Then prove
one representative heavy cut from real retained certificate data through bounded
implementation shards, its public theorem, and an audited consumer. This is a
real cut proof, not a whole-case claim with the other eleven cuts assumed away.
Select the cut by avoidable closure and representative dependencies; batch sizes
are measured tuning parameters, not an additional mathematical abstraction.

**C. Test composition growth before migrating all twelve cuts.** Add a second
independently checked representative interface. Measure the consumer with one and
two interfaces, and enlarge unrelated private fixture data. Consumer cost should
follow public interface growth, not hidden implementation growth. Require a

# Bounded module refactor plan

21 October 2026. Requested outcome: verify a bounded implementation once, then
let other modules use a small checked interface without loading its certificate

plan, not a completed migration. Case1312 remains pending; totals remain 1142

## Decision and the first gate

Prefer stock Lean separate compilation with real public/private module boundaries.
Do not continue treating importer allocation changes as the architectural fix.
A small namespace, a private declaration in a legacy file, or a tiny wrapper that
imports a large legacy bank does not establish this boundary.

There is an important compatibility gate. Both Lean and Mathlib are pinned to
4.24.0. Its installed `Lean/Environment.lean`, at `subsumesInfo`, explicitly
allows a theorem to be weakened to an axiom in its exported presentation. Its
module importer also rejects a direct non-module import from a module root.
Consequently we cannot just add `module` to a wrapper around the old libraries,
nor accept the exported view using our current proof-value axiom collector as
though it still contained every private proof.

Official Lean 4.30 release notes document restoration of module-aware
`#print axioms` by computing dependencies during serialization:
https://lean-lang.org/doc/reference/latest/releases/v4.30.0/
That identifies a relevant upstream facility, not permission to change the
project toolchain or substitute an incomplete audit. Choose an exact matched
Lean/Mathlib version only after a small compatibility pilot. Expect a versioned
audit/toolchain migration may be needed for genuine hidden implementations.
Do not invent handwritten axiom interfaces or silently exempt interface names
from the standard-axiom gate.

First deliverable: a fresh producer, consumer and private dependency, built with
stock Lean, demonstrating all of the following together:

1. The producer implementation is kernel checked; its real axiom dependencies
   are fully accounted for across the private boundary.
2. The consumer imports a proved public theorem while the private bank and its
   helper constants are absent from the consumer environment.
3. Every public type is well formed using the small public dependency closure;
   public signatures contain no private certificate/table/auxiliary proof names.
4. A private replacement whose exported artifact is byte-identical requires new
   producer evidence but does not recompile the unchanged consumer. Measure
   actual artifact stability rather than assuming every private edit preserves it.
5. An injected private axiom, missing implementation evidence and mismatched
   public/private artifacts each fail acceptance. An invalid theorem fails the
   kernel. No native_decide, sorry, ad hoc trusted checker or missing-proof waiver.

A raw collector result that merely reports an exported theorem as an axiom is
not a successful pilot. Any module-aware audit adaptation must be a versioned,
independently checked acceptance path, preserving the allowed axiom set and
complete dependency accounting. Keep the existing legacy gate and receipts intact.
If this cannot pass on 4.24, record that result and the precise upgrade scope;
source-only sharding is useful preparation but does not count as achieving the
requested implementation boundary. No whole-project upgrade is part of planning.

## Target dependency structure

The permitted direction of mathematical dependencies is:

    small semantic definitions + generic checking/soundness lemmas
                         |                       |
                private bounded data     private implementation proofs
                         |_______________________|
                                     |
                           small proved interfaces
                                     |
                           case1312 composition
                                     |
                          occasional case union

The consumer imports exported interfaces, not their private implementation
closures. This distinction must be observed in its actual loaded environment.
The implementation can use other small proved interfaces privately; it must not
need one huge private bank merely to check its own bounded certificate batch.

* **Semantic base.** Placement labels, compatibility, exclusions, finite masks,
  trace rules and their soundness statements. Keep this free of generated case
  banks, concrete pilot examples and audit-command definitions. For example,
  `GeometryRowAngleKeyV2.All` currently mixes its generic transport with imports
  of three concrete pilot banks; its replacement should separate those roles.
* **Private data/checking shards.** Bounded certificate records, required row
  identities and local dictionary entries. Copy proposed data from the retained
  search evidence, then check it in Lean; Python selection or an old JSON hash
  supplies no mathematical proof. Deduplicate canonical keys within shards and
  share small semantic interfaces across shards, rather than exporting a single
  all-cases data table. Avoid one file per row.
* **Cut interfaces.** For each case1312 cut, export its small owner/blocker masks
  and a theorem excluding the stated compatible pairs. Keep support rows,
  certificate indices and intermediate identities private. Where masks must

  the public conclusion depend on unfolding a hidden certificate representation.
* **Terminal/coverage interfaces.** Export the actual 728-choice terminal result

* **Operational audit support.** Share one versioned audit command implementation

The intended case-facing surface is about 12 cut results plus terminal/coverage
